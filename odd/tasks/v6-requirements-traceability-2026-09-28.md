# Muttu Hub v6 — Requirements Traceability Audit

Scope: independent trace of every discrete requirement in the four requirement sources against the `Muttu Hub v6.dc.html` prototype, cross-checked against the design bundle's own `referencia/Auditoria v6.dc.html`.

---

## (a) Methodology / sources note

**Sources read in full (verified facts below are grounded in direct reads of these exact files):**

1. `uploads/Requerimientos Funcionales - Detalle Clientes.docx` → extracted to plain text (2,750 chars). Cited as **DetCli**.
2. `uploads/Requerimientos Funcionales - Tablero de Seguimiento y Gestión Social.docx` → extracted to plain text (5,686 chars). Cited as **Tablero**. **Verified byte-identical (sha256 `8c53d9b0…`) to `uploads/req-tablero.docx`** — treated as one source; the duplicate copy is noted but not re-analyzed.
3. `uploads/Muttu_Hub_PRD_v2.md` (1,076 lines, read in full). Cited as **PRD§n**.
4. `uploads/Muttu-Hub-UIUX-Spec.md` (320 lines, read in full). Cited as **UIUX§n**.
5. `design_handoff_muttu_hub_v6/Muttu Hub v6.dc.html` (1,387 lines) — read in full, including the embedded `data-dc-script` JS (the actual interaction logic and mock data, not just the markup). This is the ground truth for "what v6 does."
6. `design_handoff_muttu_hub_v6/README.md` (204 lines, read in full) — the handoff's own screen-by-screen documentation and requirement mapping.
7. `design_handoff_muttu_hub_v6/referencia/Auditoria v6.dc.html` — **verified byte-identical** (sha256 `05f7e8ba…`) to the top-level `Auditoría v6 - Código, requerimientos y plan.dc.html`; read once, embedded script fully extracted. This is the design bundle's own code-vs-requirement trace, used only as a cross-check (per task instructions), never as ground truth.
8. Lower-priority historical context, partially read (embedded script only, no full prose pass): `Requerimientos vs pantallas.dc.html` (traces **v3** design — labeled `Diseño v3` in its own data), `Pantallas - Documento Clientes.dc.html` and `Pantallas - Documento Proyectos.dc.html` (both trace **v5** design — labeled `En v5`). These are superseded snapshots, used only to confirm whether a v6 gap/decision is new or long-standing.

**Not read:** other files in the extraction folder (v2/v3/v4/v5 prototypes, `Roadmap CRM.dc.html`, screenshots, `.jsx` files) — out of the confirmed inventory for this task.

**Important scope note about the Auditoría cross-check:** the Auditoría's own `REQ` trace table covers **only** the two docx documents (`RF-C01–C04`, `RNF-C01–C02`, `RF-01–07`, `KPI 1–6`, `RNF-01–03`) against the **actual MuttuHub-CRM codebase** and v6 design. It does **not** trace PRD v2 or the UIUX Spec against v6 at all. So for everything sourced from PRD§/UIUX§ below, there is no Auditoría opinion to disagree with — that entire slice of this report is independent territory the Auditoría never covered. This is stated as fact (confirmed by reading its full `REQ`/`PANT`/`DEC` arrays), not an assumption.

**Verified vs inferred, throughout:** a finding marked "Verified" means I quote or paraphrase exact text/markup/JS I read. A finding marked "Inferred" means I reasoned from indirect evidence (e.g., absence of a keyword across all sources, or a UI pattern implying a business rule not stated anywhere). Ambiguous cases are flagged explicitly as ambiguous, not silently resolved.

## (e) Disagreements with the Auditoría's own trace

The Auditoría (`referencia/Auditoria v6.dc.html`) is generally careful and its `REQ`/`PANT`/`DEC` conclusions matched my independent read in the large majority of cases (e.g., it independently reaches the same conclusions I did on Contradictions #1, #3, #4, and on the Convocatorias/Salud/Mapa/Relaciones scope questions). Below are the specific places where my independent read **diverges** from its stated conclusions, with the evidence for each.

1. **Technical semaphore formula (relates to Contradiction #5).** The Auditoría's `DEC` array states, verbatim: *"Umbrales del semáforo técnico… v6 usa ≥ 90 %, 70–89 % y < 70 %."* This is the **ratio**-based description. I read the actual embedded JS logic that drives every traffic-light color in v6 (`sem = (p, r) => r - p >= -5 ? ok : r - p >= -20 ? warn : bad`) and it is **not** a ratio rule — it is a point-difference rule, and it is the *only* formula actually wired to any pixel in the prototype (the ratio framing appears only as static label text on the Admin→Semáforos screen and in the README, never as executable logic). The Auditoría appears to have copied the Admin screen's/README's stated description rather than checking the executable behavior, and so inherited the same internal inconsistency I flag in Contradiction #5, rather than catching it. **This is a genuine disagreement, not a difference of opinion**: one of the two descriptions must be wrong about what the prototype actually does, and I am reporting the one I verified against the executable source, which is the point-difference rule.

2. **Auditoría's "Roles" row scope.** The Auditoría's `REQ` table entry for `Roles` states the code's roles as "ADMINISTRADOR, GERENCIA, COORDINADOR, COLABORADOR + 2 flags" and marks the **UI trace ('u' column) as 'p' (parcial)** rather than pointing out that this is a full **4-vs-4 role-model replacement** in the *design*, not merely a partial-completeness gap. My read treats this as more than "partial" — v6 does not partially implement the docx's 3-role model or the PRD's 4-role model; it implements a **fourth, distinct** vocabulary that happens to be reconcilable via permission flags. I'd characterize this as "reconciled by convention, not by matching names," which is a more precise (and slightly more concerning, from a spec-fidelity standpoint) characterization than a flat "Parcial" rating suggests. This is a difference of **emphasis/interpretation**, not a factual disagreement — the Auditoría's underlying facts (4 roles + 2 flags in code, 4 profiles in v6, mismatched names) are the same facts I found.

3. **Scope coverage of PRD v2 and UIUX Spec.** This is not a disagreement so much as a **coverage gap**: the Auditoría's `REQ` table has exactly 24 rows, all sourced from the two docx (`cli`/`tab` document tags only — verified, no PRD or UIUX rows exist in the `REQ`, `PANT`, `BRE`, or `DEC` arrays). Every finding in section B3 and B4 of this report that touches PRD-only or UIUX-Spec-only requirements (the missing Compromisos/Bitácora/Documentos/Tareas-relacionadas tabs on the client sheet, the missing Dashboard "4 caras," the missing AI-Brief-upload flow, the Ley 1581 compliance gap, the color-token contradiction, the Kanban 5-column violation, the Next.js version conflict, the "tres vs. cuatro caras" Spec-internal drop) **has no counterpart opinion in the Auditoría at all** — it simply never looked at those two documents. This is stated as a verified fact about the Auditoría's scope (I read its full data arrays and confirmed no PRD/UIUX-tagged rows exist), not an inference about what it "probably" missed.

4. **Auditoría does not flag the "Solicitudes" (access-request queue) as an undisclosed addition.** The Auditoría's `PANT` (screens) table does not include a row for the Administración→Solicitudes tab at all — it is simply absent from its screen inventory, whereas Convocatorias/Salud/Mapa (which *are* rows, marked 'f'/"Solo en diseño") were caught. This isn't a contradiction of a stated conclusion, but an **omission** relative to my independent screen-by-screen read of v6's Administración tabs (which I read the full script for, including the `atSol`/`solicitudes` state). I flag it because the task specifically asks for scope-creep the Auditoría might have missed.
