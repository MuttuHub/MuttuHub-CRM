# Muttu Hub v2 — Projects module (RF v2.0) and Clients/Opportunities — development plan

Status: PLAN ONLY (2026-09-29). Nothing implemented. No code, schema or migration changed by this document.

## Objective
Replace the unshipped v1 Projects model (Proyecto → Meta → Actividad + LineaPresupuestal + Gasto +
Indicador + SoporteProyecto, never released) with the PO's RF v2.0 target model (Proyecto → Objetivo → Actividad in
relative weeks → Entregable → Avance → Medio de verificación; Rubro budget + monthly programming;
validated expenses; baseline + approved, versioned modifications), and close the residual gaps of the
Clients/Opportunities requirements, **incrementally, in vertical slices**, without a big-bang rewrite and
without a v1 module to keep working — the v1 Projects module was never shipped.

## Problem
- The v1 model was designed from RF v1.0 (2026-09-04) but was never shipped. RF v2.0 (2026-09-28) changes the technical
  hierarchy, the week-based schedule, the budget model, the financial semáforo semantics (optimal spend
  instead of bidirectional), adds expense validation, Excel import, versioning and a Gerente approval flow,
  and drops territorial semaforización.
- The v1 Projects module was never shipped: `main` has no projects models, migrations or code, and production
  has 0 rows in `proyectos`/`metas`/`actividades`. There is no test suite to invalidate and no loaded data to
  lose, so the model is replaced **before it ever ships** and built directly on `main`.

## Why
- PO documents are mandatory scope (user direction 2026-09-29). RF v2.0 is adopted as the TARGET model.
- The visual plan (`odd/tasks/v6-visual-alignment.md`) put V2.5–V2.8 and V2.11 ON HOLD pending this plan.

### Verified current-state facts (2026-09-30)

These facts describe the abandoned v1 branches: the v1 Projects module never shipped, so `main` has no
projects models, migrations or code. They are kept because each v2 decision contrasts against them.
- F1. `Proyecto` has `codigo` (user-typed, `@unique`, not autogenerated), `territorio String` (single free
  text), `linea_estrategica` single enum `LineaEstrategica` (8 values = the RF-02 list), `estado`
  `EstadoProyecto {PLANIFICACION, EN_EJECUCION, SUSPENDIDO, CERRADO, CANCELADO}`, `beneficiarios_meta Int`,
  `umbrales_override Json?`, `oportunidad_id @unique` with composite FK `[oportunidad_id, cliente_id]`.
  **No `valor_total`, no `origen`, no municipios list, no duration.**
- F2. `Meta` (no code), `Actividad` (`fecha_planificada` single date, `fecha_real?`, `peso Int` default 1,
  `porcentaje_avance Int` 0..100). No start/end week, no Entregable, no Avance history.
- F3. `Rubro` has `nombre @unique`, `activo`, `orden`; **no `codigo`**. Seeded rows: Personal, Transporte,
  Material POP, Operación logística (migration `20260918153200`). RF v2.0 explicitly removes the last two.
- F4. `LineaPresupuestal.monto_proyectado_cop Decimal(15,2)`; no per-period programming.
- F5. `Gasto`: `concepto`, `monto_cop`, `fecha_gasto`, `tercero?`, `numero_comprobante?`, `observado`,
  `observacion?`; legalization state derived (`observado` / `con_soporte` / `falta_soporte`). No
  Registrado/Validado/Rechazado, no validator, no support type, no third-party ID type/number, no period.
- F6. `Indicador`: `meta_id?`, `meta_valor`, single `valor_actual?` (no measurement history),
  `cuenta_beneficiarios` flag (beneficiaries derived from indicators, not a count registry).
- F7. `SoporteProyecto`: XOR `storage_path` / `url_externa`, `actividad_id?` / `gasto_id?`, composite FKs
  `[x_id, proyecto_id]`; files served via signed URLs (attachments route). `documento_id?` mirror to Documentos.
- F8. `semaforo.ts`: `colorTecnico` is ratio-based (real/programado vs `tecnico.verde`/`tecnico.rojo`);
  `colorFinanciero` is **bidirectional** (band `verde_min..verde_max`) → **conflicts with RF-24** (spending
  less is not a deviation). Thresholds live in `Setting["semaforo_umbrales"]` + per-project override.
- F9. Roles: `RolUsuario {ADMINISTRADOR, GERENCIA, COORDINADOR, COLABORADOR}`; `MANAGE_ANY_ROLES` =
  ADMINISTRADOR, GERENCIA, COORDINADOR. Orthogonal flags `gestiona_oportunidades`,
  `puede_ver_tablero_gerencial`. `canViewProject` = management-dashboard reader OR `responsable_id`.
  `canCreateProject` = manage-any roles. No approval role concept.
- F10. `Auditoria` stores a light snapshot of sent fields (`cambios Json`), **not** before/after per field,
  and is not DB-enforced append-only → gap vs RF-04 / RNF-05.
- F11. Project from opportunity: `POST /clients/:id/opportunities/:oid/project` requires
  `Oportunidad.fase = EJECUCION` (set by the separate `convert` action), not `estado = GANADA`; nothing is
  prefilled server-side except `cliente_id`/`oportunidad_id`.
- F12. `exceljs ^4.4.0` is already a dependency (Excel generate/parse available). Next 16.3.0, Prisma 7.9.
- F13. `Tarea` has no link to Proyecto/Actividad (RF v2.0 "activities NOT linked to task management": already true).
- F14. Open openspec changes touching projects: `proyecto-financiero-tab`, `proyecto-legalizacion-tab`
  (5 open tasks), `proyecto-metas-tab`, `proyecto-soportes-tab`, `tablero-gerencial-unificado`,
  `admin-umbrales-editables`. All are built on the v1 model, which was never shipped and is being abandoned.
- F15. Test impact: none in this branch. There are no v1 project tests to inventory, because the v1 module was
  never shipped; the previously planned inventory task (S0.2) was removed with the direct path.
- UNVERIFIED: remote `.env` Supabase row counts for projects (must not be queried by agents; the user runs
  counts there only if they choose to), exact `storage` bucket name/policies for SoporteProyecto.

## Target domain model (summary, from Estructura §2–§7)
- Proyecto: codigo (autogen PRY-AAAA-NNN, format Pendiente), origen {OPORTUNIDAD, INDEPENDIENTE},
  oportunidad 0..1, cliente, nombre, responsable, líneas N..N (DP-05), municipios N..N (informative),
  fecha_inicio/fin, duracion_semanas (calc), valor_total Decimal, meta_beneficiarios Int,
  estado {BORRADOR, EN_EJECUCION, CERRADO} (+ SUSPENDIDO, CANCELADO Propuesto), baseline/version pointers.
- Objetivo (OEn) → Actividad (código 1.1, semana_inicio/fin, peso Decimal, responsable?, calc dates/state)
  → Entregable (código, cantidad Decimal > 0, unidad, tipo de medio exigido) → Avance (fecha, cantidad,
  observación) → Medio de verificación (file | link).
- Objetivo → IndicadorResultado (código, meta, unidad, línea base?) → Medición (fecha, valor, soporte?).
- RegistroBeneficiarios (fecha, cantidad, actividad?) — count only, no personal data.
- Rubro (código immutable, nombre, estado Activo/Suspendido) → PresupuestoRubro (A) → ProgramacionPeriodo (P, AAAA-MM).
- Gasto (rubro, periodo, fecha documento, tipo soporte, tercero nombre + tipo/número ID, número documento,
  descripción, valor, estado Registrado/Validado/Rechazado, validador/fecha/motivo) → Soporte (file | link).
- Version (número, tipo línea base/modificación, solicitud?, aprobador, snapshot JSONB) ;
  SolicitudModificacion (tipo, motivo, detalle antes/después, estado, decisión) ; AuditoriaCambio append-only.
- Execution records (avances, mediciones, beneficiarios, gastos) are NOT versioned; they are compared
  against the chosen version (original v0 or current).

## Schema evolution (no v1→v2 data migration)

The v1 Projects module was never shipped: `main` has no projects models in `prisma/schema.prisma`, no projects
migrations, and no projects code at all (`src/lib/semaforo.ts`, `src/lib/api/projects.ts`,
`src/app/api/v1/projects/**` and `src/components/proyectos/**` are all absent — VERIFIED 2026-09-30 on
`main` @ `11e9bc1`). Production has 0 rows in `proyectos`/`metas`/`actividades`. There is therefore **no data to
migrate and no coexistence to manage**: the v2 model below is the only Projects model that will ever exist in
code, and it is built directly on `main`.

- **Additive migrations, applied directly**: new tables and nullable/defaulted columns, composite uniques
  `[id, proyecto_id]` and composite FKs on every child, CHECK constraints in SQL (Prisma does not model CHECK).
- **Catalog and default scripts** (`scripts/migrate-v2/*.ts`) still exist for the rubro catalog (R01–R15 plus
  the suspended legacy rubros), municipios and the `$0` budget rows: idempotent, **count-first dry-run**
  (`--dry-run` prints per-table counts and every row needing a human decision, writes nothing), then `--apply`
  in one transaction. Runs only with `--env-file=.env.local` and the localhost guard.
- **No v1 table or column is dropped**, because none of them exist in this branch. The expand/backfill/switch/
  contract sequence and the `projects_v2` flag were removed with the direct path — see
  `odd/tasks/v2-projects-sdd.md` §5.13 and `odd/tasks/v2-projects-execution.md`.
- **Storage invariants**: no script ever deletes or moves a storage object; orphan check (rows whose
  `storage_path` has no object, and objects with no row) is reported, never auto-fixed (S0.6).
